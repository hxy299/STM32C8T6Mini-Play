# STM32 下位机 M0 ~ M2.5 上板验收说明

> 对应项目说明书 §10 的前四个阶段。
> **本阶段不驱动任何执行器**（步进/舵机/TOF/TTS 都未初始化），
> 只需要 **MCU 板 + ST-Link + 3 根杜邦线** 就能验证全套逻辑。

## 1. 接线（只有 3 根信号线 + 3 根下载线）

### 1.1 与 PC 通信（USB-TTL 串口模块）

```
USB-TTL                STM32F103C8T6
  RXD  ←──────────────  PA9  (USART1_TX)
  TXD  ──────────────→  PA10 (USART1_RX)
  GND  ───────────────  GND
```

```
  GND    ────────────  GND
```

## 3. M0 验收：骨架

### 3.1 判据

| 检查项 | 合格标准 |
|---|---|
| 串口有开机横幅 | 看到 `A733 DeskPet Motion MCU` |
| **时钟** | 横幅里 `SYSCLK : 72000000 Hz  [OK]` |
| **LED 心跳** | 板载 LED（PC13）**1 Hz 稳定闪烁**（约 0.5 s 亮、0.5 s 暗） |
| 上电指示 | 开头有 **3 次快闪** |

### 3.2 预期串口输出

```
========================================
 A733 DeskPet  Motion MCU  (STM32F103C8T6)
 stage: M0 ~ M2.5  (skeleton, no actuator)
----------------------------------------
 SYSCLK : 72000000 Hz  [OK]
 link   : USART1 115200 8N1  PA9(TX)/PA10(RX)
 tick   : TIM3 1ms   IWDG: ~1.6s
 config : 0x0000007A  (default)
   SERVO=0 TTS=1 BT=0  TOF0/1/2/3=1/1/1/1
========================================
 ready: waiting for frame A5 01/08/06 ...
```

> `config : 0x0000007A` 是默认值（SERVO/BT 关闭，TTS 与 4 颗 TOF 开启）。
> 首次上电显示 `(default)`；写入过一次后应显示 `(from flash)`。

### 3.3 若 LED 不闪

| 现象 | 原因 | 处理 |
|---|---|---|
| LED 完全不亮/不闪 | 时钟没跑到 72 MHz，或 TIM3 中断没进 | 先看串口里 `SYSCLK` 是不是 `[!!]` |
| 常亮 | `LED_ACTIVE_LOW` 极性反了 | 改 `app_config.h` 的 `LED_ACTIVE_LOW` 为 0 |
| 闪但很快 | 进了故障态 | 看串口 `[stat]` 行的 `fault=` |

## 4. M1 验收：串口链路 + CRC

### 4.1 准备

```bash
pip install pyserial
```

### 4.2 一键自检（最推荐）

```bash
python tools\pc_link_test.py COM4 --selftest
```

（`COM4` 换成你实际的串口号）

### 4.3 预期结果

```
[PING] 保活并读取状态
  --> TX A501010006 00 ...
  <-- RX   TYPE=2 SEQ=1 OP=0x86(PONG) LEN=9  uptime=0s  fault=0x00(NONE)  config=0x0000007A [...]

[GET_CONFIG] 读取当前功能开关
  <-- RX   TYPE=2 SEQ=2 OP=0x87(CONFIG) LEN=4  config=0x0000007A [...]

[SET_CONFIG] 翻转 TTS 位以验证 Flash 持久化
  <-- RX   TYPE=2 SEQ=3 OP=0x81(ACK) LEN=1  status=0x00(OK)

[MOVE] 本阶段应返回 NAK(NOT_IMPLEMENTED)
  <-- RX   TYPE=2 SEQ=5 OP=0x82(NAK) LEN=2  status=0x08(NOT_IMPLEMENTED)  detail=0x01(MOVE)

[坏 CRC] 应被拒（不产生应答，坏帧计数增加）
  ✓ 无应答（正确）
```

### 4.4 M1 的硬判据

| # | 判据 | 怎么确认 |
|---|---|---|
| 1 | PING → PONG，且 `seq` 回显正确 | 自检输出 |
| 2 | GET_CONFIG → CONFIG，4 字节配置 |
| 3 | SET_CONFIG → ACK，并跟随一条 `EVT_CONFIG_CHANGED` |
| 4 | **故意改坏 1 个字节 → 必须无应答** | 自检的"坏 CRC"项 |
| 5 | 串口 `[stat]` 行的 `good` 计数随每次请求增加 | 看 5 秒一次的状态行 |

### 4.5 手动验证 CRC（不依赖工具）

用任何串口助手，**十六进制发送**：

```
A5 01 07 00 06 00 E3 FD
```

这是 `PING`（seq=7）。预期收到：

```
A5 02 07 00 86 09  <uptime×4> <fault> <config×4> <crc_lo> <crc_hi>
```

然后把最后一个字节 `FD` 改成 `FE` 再发一次 —— **应该完全没反应**（CRC 被拒）。
这就是判据 4。

## 5. M2 验收：心跳超时 + 看门狗

### 5.1 心跳超时

| 步骤 | 预期 |
|---|---|
| 1. 正常通信（每 0.5 s 发一次 PING） | LED **1 Hz 慢闪**，`[stat]` 显示 `LINK` |
| 2. **停发 1 秒以上** | 收到一条 `EVT_FAULT`，`fault=0x01(HEARTBEAT_LOST)` |
| 3. 观察 LED | **变 5 Hz 快闪**（`LED_FAULT_MS = 100`） |
| 4. 重新发一次 PING | 故障清除，LED 恢复 1 Hz 慢闪 |

> 注意：上电后有 **3 秒宽限期**（`APP_BOOT_BANNER_MS`），
> 这期间不接 PC 也不会立刻报故障。

### 5.2 看门狗

这是**必须单独验证**的一项：

1. 在 `main.c` 的 `while(1)` 循环开头**临时**插入 `while(1){}`
2. 重新编译烧录
3. **预期**：约 **1.6 秒**后板子自动复位（重新打印横幅、LED 重启 3 次快闪）
4. **验证完必须删掉这个死循环**

> 如果板子卡死不复位，说明 IWDG 没起来 —— 检查 `BSP_IwdgInit` 是否被调用。

## 6. M2.5 验收：配置持久化（**最关键的一项是断电重启**）

### 6.1 步骤

```
1. python tools\pc_link_test.py COM4
2. cmd> g                     # 读当前配置，记下这个值（例如 0x0000007A）
3. cmd> s 00000078            # 关掉 TTS（翻转 bit1），其它不变
4. cmd> g                     # 确认回读是 0x00000078
5. cmd> q
6. ★★★ 拔掉 USB，等 3 秒，再插上 ★★★
7. python tools\pc_link_test.py COM4
8. cmd> g                     # 必须仍然是 0x00000078
```

### 6.2 判据

| # | 判据 |
|---|---|
| 1 | `SET_CONFIG` 成功返回 ACK |
| 2 | 立即 `GET_CONFIG` 回读到新值 |
| 3 | **断电重启后 `GET_CONFIG` 仍是新值** ← 这一条才算真持久化 |
| 4 | 横幅里从 `(default)` 变成 `(from flash)` |
| 5 | 连续写 100 次不损坏（可选，自检已覆盖逻辑） |

### 6.3 盲走模式验证（配置系统的安全联动）

```
cmd> s 00000006        # 00000110 = 只有 TTS 和 BT，底部三颗 TOF 全关
```

预期：

1. 横幅/状态出现 `WARN : bottom TOF all disabled -> BLIND MODE`
2. `PING` 返回 `fault=0x0A(NO_EDGE_PROTECT)`
3. `CLEAR_FAULT` **不带** `blind_ack` → 返回 **NAK**
4. `CLEAR_FAULT` **带** `0x5A` → 返回 ACK
5. **重启后重新要求确认**（不会记住上次的放行）

验证完记得恢复：`cmd> s 0000004E`

## 7. 故障排查表

| 现象 | 最可能原因 | 处理 |
|---|---|---|
| 串口完全没有输出 | ① 波特率不对 ② TX/RX 接反 ③ 没烧进去 | 量 PA9 空闲应约 3.3 V；把 RXD/TXD 对调试试 |
| 输出乱码 | 波特率或时钟不对 | 确认 `SYSCLK : 72000000 Hz [OK]` |
| LED 不闪 | TIM3 中断没进 / 极性反 | 见 §3.3 |
| 发 PING 无应答 | CRC 算法不一致 | 用 §4.5 的固定帧 `A5 01 07 00 06 00 E3 FD` 测试 |
| 有应答但 `seq` 不对 | 帧头偏移 → 前导垃圾 | 看 `[stat]` 的 `bad` 计数是否在涨 |
| `SET_CONFIG` 后重启又回默认 | Flash 写失败 | `[stat]` 里看是否有 `STATUS=FLASH_FAIL`；也可能是假片 |
| 板子周期性复位 | 喂狗不够 / 死循环 | 检查主循环是否卡在某个阻塞调用 |
| 编译报 `#error select first the target` | Define 丢了 | 见 §2.1 |

## 10. 附：固定测试向量（用于核对 CRC 实现）

| 用途 | 帧十六进制 |
|---|---|
| PING, seq=7 | `A5 01 07 00 06 00 E3 FD` |
| GET_CONFIG, seq=0 | `A5 01 00 00 08 04 01 02 03 04 14 9C` |
| 往返测试, seq=0x1234, op=6, payload=01..05 | `A5 01 34 12 06 05 01 02 03 04 05 47 AB` |

> 最后一行是 CRC-16/CCITT-FALSE 的标准检验值。

## 11. 补充：LED 三种节奏 + 关于 EVT_FAULT 刷屏（2026-10 实机反馈后新增）

### 11.1 LED 三种节奏（可肉眼区分状态）

| 节奏 | 含义 | 波形 |
|---|---|---|
| **1 Hz 慢闪** | 通信正常（`fault=0`） | 亮 500 ms / 灭 500 ms |
| **双闪 + 长停** | 上电后**从未**收到过上位机帧 | 亮 100 / 灭 150 / 亮 100 / 灭 850（1.2 s 一轮） |
| **5 Hz 快闪** | **曾经**通信过，现在丢失；或其它故障 | 亮 100 ms / 灭 100 ms |

> 为什么区分"没接"和"掉了"：上电不接上位机时，固件会按**安全策略**置
> heartbeat 故障（这是对的），但肉眼能分开这两种情况可以省很多排查时间。

### 11.2 关于 `EVT_FAULT` 在串口里反复出现

自检时你会看到大量：

```
<-- RX TYPE=3 SEQ=0 OP=0x93(EVT_FAULT) LEN=1  fault=0x01(HEARTBEAT_LOST)
```

**这是正常现象，不是 bug。** 原因：

```
PC 工具每条命令后 idle 1.0 ~ 1.5 秒等待应答
下位机心跳超时阈值正好是 1000 ms
→ 每次 idle 都触发一次心跳超时 → 主动上报一条 EVT_FAULT
```

在实际系统里 A7Z 每 **500 ms** 发一次 PING，不会触发。

可调参数：`app_config.h` 的 `HB_TIMEOUT_STOP_MS`（默认 1000）。
台架手工调试嫌频繁可临时改大（例如 3000），**但正式联调前必须改回 1000**。

### 11.3 ⚠️ 串口里的 4 个乱码 `▒▒▒▒` 是什么

那是 **`EVT_FAULT` 二进制帧**被文本终端显示了：

```
A5 03 00 00 93 01 01 <crc_lo> <crc_hi>
│  │        │  │  │
│  │        │  │  └ 故障码 0x01 = HEARTBEAT_LOST
│  │        │  └ payload 长度 1
│  │        └ 操作码 0x93 = EVT_FAULT
│  └ 事件帧类型
└ 帧头 SOF
```

`A5` / `93` / 两个 CRC 字节为高位字符，文本终端会显示成 `▒`，正好 4 个。
**看到它说明发送链路是通的。**

### 11.4 `uptime` 的单位

PONG 里的 `uptime` 单位是**毫秒**（uint32，约 49 天溢出）。
`pc_link_test.py` 会同时显示秒和毫秒：

```
uptime=191.651s (191651ms)
```

> 早期版本的工具把这个值直接标成 `s`，会显示成 `191651s`（看着像 53 小时）。
> 已修正。若你看到异常大的秒数，先用毫秒值核对。

### 11.5 台架自检的推荐姿势

```bash
# 1) 先关掉串口助手，否则 COMx 被独占会报 PermissionError(13)
# 2) 跑工具自检
python tools\selftest_pc_tool.py
python tools\pc_link_test.py COM5 --selftest
```

若 `PermissionError(13, '拒绝访问')`：**串口被别的程序占着**，
关掉串口助手 / Keil 的 Debug 窗口 / 其它终端即可。

### 11.6 走串口助手手工验证（不依赖 Python，最简单）

串口助手切到 **HEX 发送**，依次发：

| 目的 | 发送（HEX） | 预期 |
|---|---|---|
| PING | `A5 01 07 00 06 00 E3 FD` | 收到 `A5 02 07 00 86 09 ...` |
| GET_CONFIG | `A5 01 00 00 08 00 A9 62` | 收到 `A5 02 00 00 87 04 7A 00 00 00 ...` |
| 坏 CRC | `A5 01 07 00 06 00 E3 FE` | **完全没有反应**（最后一位故意改成 FE） |

第三条就是 M1 的关键判据：**坏 CRC 必须被静默丢弃**。

## 12. ⚠️ M2.5 断电持久化：为什么"拔 USB"测不出来（重要）

### 12.1 实测踩到的坑

第一次按"拔 USB 再插上"测试时，日志是：

```
uptime=7.695s  config=0x00000078
uptime=16.442s config=0x00000078
uptime=23.768s config=0x00000078
```

看起来"配置保住了"，但 **`uptime` 是单调递增的**（7.7 → 16.4 → 23.8，
间隔约 8 s、7 s）。如果真断电重启过，uptime 必须回到 0 附近。

**结论：板子根本没重启，配置还在 RAM 里，这次测试无效。**

原因：拔掉的是 **USB-TTL 模块的 USB 线**，而 MCU 由 **ST-Link 的 3.3 V** 供电，
拔 USB-TTL 不会让 MCU 掉电。

### 12.2 正确的断电方式（任选一种）

| 方式 | 操作 |
|---|---|
| **按 RESET 键**（最省事） | Blue Pill 上标着 `R` 或 `RESET` 的按键 |
| **断开 MCU 的全部供电** | 同时断开 ST-Link 的 3.3 V **和** 板子的 USB |
| Keil 里复位 | Debug 状态下点 Reset |

> ⚠️ 只拔 USB-TTL 的数据线不算断电。

### 12.3 用 `--verify-boot` 一次性判定（推荐）

固件在 PONG 里新增了第 10 个字节 `flags`：

| 位 | 含义 |
|---|---|
| bit0 | **配置来源**：1 = 从 Flash 加载；0 = 用默认值 |
| bit1 | **盲走模式**：1 = 底部三颗 TOF 全关 |

用法：

```bash
python tools\pc_link_test.py COM5 --verify-boot
```

**通过时的输出：**

```
  uptime   : 2.153 s
  config   : 0x00000078 [TOF0_bottom_front, TOF1_bottom_left, TOF2_bottom_right, TOF3_front_obstacle]
  flags    : 0x01
    bit0 配置来源 : Flash
    bit1 盲走模式 : NO

  ✓ uptime 较小（2.153 s），看起来是刚启动
  ✓ 配置来自 Flash → 持久化成功

 结论：FLASH 持久化 通过
```

**两条自动判据：**

1. `uptime > 60 s` → 判定"没重启过"，测试无效，直接告诉你按 RESET
2. `flags bit0 == 0` → 判定"配置来自默认值"，持久化失败

这样就不需要靠"看横幅"或"肉眼比 uptime"来猜了。

### 12.4 如果 `flags bit0 == 0` 且确实重启过

那说明 Flash 写入或回读有问题。排查顺序：

| 可能原因 | 验证方法 |
|---|---|
| **32 KB 假片**（`0x0800FC00` 超出物理 Flash） | 读 `DBGMCU->IDCODE` 或用 `--ping` 看是否连 `config` 都读不出 |
| FLASH 擦写失败 | `SET_CONFIG` 应返回 `NAK(0x07 FLASH_FAIL)`；若返回 ACK 说明写成功了 |
| 校验逻辑不匹配 | 打开 `APP_DEBUG_TEXT` 后串口会打印 `[link] first frame OK`，配合横幅看 `(default)` / `(from flash)` |

> 若确认是 32 KB 假片，把 `app_config.h` 里的
> `CFG_FLASH_ADDR` 从 `0x0800FC00` 改成 `0x08007800`（32 KB 片的最后一页）即可。
